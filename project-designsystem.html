00 — Overview

项目背景

在多个项目并行开发的过程中，我逐渐发现每次从零定义颜色、字体、间距等样式变量不仅耗时，而且难以保证跨项目的一致性。设计稿中的蓝色，在开发落地时常常出现色值偏差；同样的圆角半径，在不同组件中参差不齐。

受 Material Design 3 的 Token 分层理念和 Apple Human Interface Guidelines 的启发，我决定构建一套属于自己的设计令牌（Design Tokens）体系。这不是一个单纯的上游设计规范，而是一套可编码、可版本管理、可跨平台同步的原子化设计语言。

最终产出了一套覆盖色彩、字体、间距、阴影、圆角等维度的完整令牌体系，并通过 Style Dictionary 工具链实现多平台代码输出（CSS Custom Properties + JSON）。

01 — Token Structure

三层令牌架构

借鉴 Material Design 3 的设计令牌分层思想，将整个体系拆分为三个抽象层级。每一层独立管理和演化，上层引用下层，确保修改一处即可全局生效。

🔵

Primitive Tokens · 原始令牌

最底层的原始值，如具体的 HEX 色值、像素字号、像素间距。不与任何语义绑定，是所有设计的「原子」素材。例如：blue-500: #3B82F6、spacing-4: 16px。

🟢

Semantic Tokens · 语义令牌

中间层，将原始令牌赋予功能语义（用途/情感/角色）。此时颜色不再叫 "blue-500"，而是 "color-primary"。语义令牌是设计决策的真正载体，也是明暗模式切换的关键层。

🟣

Component Tokens · 组件令牌

最顶层，为每个 UI 组件定义专属令牌，如 button-bg-color、card-border-radius。组件令牌引用语义令牌，语义令牌引用原始令牌，形成一条完整的依赖链。

{ "color": { "blue": { "500": {"value": "#3B82F6"}, /* Primitive */ "600": {"value": "#2563EB"} } }, "semantic": { "primary": {"value": "{color.blue.500}"}, /* Semantic */ "primary-hover": {"value": "{color.blue.600}"} }, "component": { "button": { "bg": {"value": "{semantic.primary}"} /* Component */ } } }
02 — Color System

色彩系统

03 — Typography

字体系统

05 — Documentation

文档站点

为了让这套设计令牌体系真正可用，我搭建了一个类 Storybook 结构的设计系统文档站点。每个令牌、每个组件都有独立的展示页，支持实时预览和代码复制。文档站点本身也使用这套令牌进行样式控制，实现「自身即示例」的自我证明。

文档站点包含：色彩页面（含对比度检测）、字体排版展示、间距系统可视化、组件 API 文档、明暗模式切换演示。

06 — Reflection

总结与反思

从零构建一套设计令牌体系的经历，让我对「设计工程化」有了更立体的理解：

命名即设计。 令牌的命名方式直接影响团队协作效率。一个好的命名既要让设计师一眼看懂（如 color-primary），也要让开发者自然联想到用途。模糊的命名如「blue-500」在跨团队协作中缺乏语义共识。

语义层是不可或缺的桥梁。 如果没有语义令牌，明暗模式切换需要在每个组件中做条件判断，维护成本极高。语义层的引入让「一键切换主题」成为可能，且不影响组件层的任何代码。

规模化的一致性需要工具链支撑。 当令牌数量超过 200 个时，手动维护已不现实。Style Dictionary 的自动化构建流水线（JSON → CSS + Android XML + iOS JSON）确保了输出的一致性和可靠性，也让设计规范的变更能够通过 Git 追溯。
